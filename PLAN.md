## architecture
storage is behind a StorageBackend trait — do not couple handlers to a concrete type.
SQLite is the only concrete implementation for now.
all handlers return Result<Json<T>, AppError>. AppError implements IntoResponse.
never use .unwrap() in handler code.

2026-05-20: Schema-bundle loader rewritten to match the 2026-05-14 design-doc shape it had drifted from. `schema.sql` previously held `PRAGMA journal_mode = WAL` at the top *and* `PRAGMA user_version = 1` near the top, and `schema::ensure_schema` ran the whole file via `execute_batch` with no surrounding transaction. A mid-bundle CREATE failure would leave `user_version = 1` paired with a partial schema, and the next open would short-circuit on the `1 => Ok(())` arm of the version gate without ever re-running the bundle. Fix: split the two ambient PRAGMAs out of `schema.sql`. `schema::ensure_schema` now runs `PRAGMA journal_mode = WAL` against the bare connection first (SQLite forbids journal-mode changes inside a transaction), then opens a `conn.transaction()` and runs `execute_batch(SCHEMA_SQL)` followed by `execute_batch("PRAGMA user_version = 1")`, then commits. Mid-bundle failure rolls the DDL *and* the version stamp back atomically; the next open sees `user_version = 0` and re-runs the (non-`IF NOT EXISTS`) bundle, which either succeeds or fails loudly on a colliding pre-existing table — the failure mode the design doc (§2 "Open path") called out. Two new in-crate tests in `schema.rs`: `ensure_schema_refuses_unknown_user_version` exercises the `other => Err(Internal(_))` arm of the version gate (previously uncovered), and `ensure_schema_rolls_back_on_mid_bundle_failure` pre-seeds a colliding `rooms` table on a fresh file, opens the store, and asserts that the bundle's transaction rolls back leaving `user_version = 0` and the pre-existing table intact.
