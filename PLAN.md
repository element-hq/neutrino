2026-05-29: Storage-side apply+persist design (Phase 6d), settled in discussion. **Concurrency:** exactly one `RoomCore` per room, owned by a per-room actor (channel inbox) that serialises applies — task-per-HTTP-request would race two applies on the same forward extremities and corrupt the DAG. HTTP handlers orchestrate (receive PDU → send to actor → await outcome → federation/response); only the txn-bound work lives in storage. **Mutable vs immutable:** persisted events + auth chains are immutable, so the provider reads inside `RoomCore::apply` (`get_event`/`auth_chain`/`state_at_heads`) need **no** write txn — they run on a pooled read connection. The mutable state (forward extremities + current_state) lives in the actor's in-memory `RoomCore`; single owner ⇒ no concurrent writer. This **supersedes the forward-looking note in the entry below**: `apply` does *not* run inside the write txn — it's read-then-mutate and the reads are immutable. The only txn-held primitive is the effect persist (write-only, short). Actor applies to a clone and adopts it only after the persist commits (crash/error safe). **Two head-sets:** `RoomCore` now tracks timeline heads (`forward_extremities`, for `prev_events`) *and* state-DAG heads (`state_forward_extremities`, for `prev_state_events`) — they diverge because a non-state event drops a state event from the timeline heads via `prev_events` without touching the state heads. Persisted as two `rooms` columns (`forward_extremities`, `state_dag_forward_extremities`). **current_state** writes the affected key only (an event changes at most one state key); the full-resolved-map path matters only once federation state-merge lands (commented). createRoom's multi-event atomicity vs feeding events singly through the actor is deferred (commented, not atomic yet). Outbox/destinations deferred to Server-Server /send. Built incrementally as PR1/PR2/PR3 (see status). 2026-05-29: **PR — `GET /_matrix/federation/v1/backfill/{roomId}`** (the last federation endpoint, sibling to `get_missing_events`). Net decisions made across the PR, all with Skye over Matrix: (1) **Storage reuse, no trait change.** Backfill = "walk `prev_events` back from the `v` seeds, seeds included, newest-first", which is exactly `DagStore::events_before`'s contract — so the endpoint is HTTP-layer-only and the frozen `StorageBackend` trait is untouched. (2) **Ordering is a priority queue keyed on `origin_server_ts`, not `depth`.** `walk_prev_events` (shared by `events_before` + `missing_events`) is a `BinaryHeap` max-priority-queue popping highest `origin_server_ts` first, ties broken by ascending `event_id` — mimicking Synapse's depth-descending backfill walk (`get_backfill_events` sorts by `(-depth, -stream_ordering)`).
